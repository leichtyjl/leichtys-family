# Leichty Family website

The permanent public website and reunion home for the Leichty family.

- Production: <https://www.leichtys.com>
- Pages hostname: <https://leichtys-family.pages.dev>
- Repository: <https://github.com/leichtyjl/leichtys-family>
- Production branch: `main`

## Architecture

```text
GitHub (main)
    ↓ automatic Git integration
Cloudflare Pages: leichtys-family
    ↓ custom domain
https://www.leichtys.com
```

The site is deliberately a dependency-free static build. Site configuration lives in `content/site.json`, the family structure lives in `content/family.json`, shared page structure lives in `scripts/build.mjs`, and the generated HTML is committed so the existing Cloudflare Pages project can continue serving the repository without a framework-specific runtime.

There is no database, public RSVP form, authentication, email service, or private family data in this milestone.

## Local setup

Requirements:

- Git
- Node.js 20 or newer
- Python 3 for the local static server

```bash
git clone https://github.com/leichtyjl/leichtys-family.git
cd leichtys-family
npm run build
npm run dev
```

Open <http://localhost:4173>.

No package installation is required. The project uses only built-in Node.js modules.

## Development

1. Create a feature branch.
2. Edit `content/site.json`, `scripts/build.mjs`, or files in `assets/`.
3. Run `npm run build` after content or template changes.
4. Run `npm test` before committing.
5. Inspect `git diff --cached` before every commit and confirm no private data or secrets are present.

The HTML files at the repository root and inside route directories are generated by `scripts/build.mjs`. Do not make lasting edits directly to generated pages.

## Testing

```bash
npm test
```

This rebuilds the site and checks that expected pages, metadata, navigation landmarks, assets, and security headers exist. Before release, also test keyboard navigation, mobile and desktop widths, all main navigation links, and the browser console.

## Deployment

Cloudflare Pages is already connected to this repository. The normal workflow is:

```text
feature branch → push → Cloudflare preview → review → merge to main → production
```

A push or merge to `main` automatically deploys production. Do not add a second Pages project, direct-upload workflow, or GitHub Actions deployment unless the existing Git integration is intentionally replaced.

After a production deployment, verify:

```bash
curl -I https://www.leichtys.com
curl -I https://leichtys.com
curl -I https://leichtys-family.pages.dev
```

Expected behavior: the canonical `www` HTTPS site returns `200`; the HTTPS apex redirects permanently to `https://www.leichtys.com/`; and HTTP is upgraded to HTTPS.

## Cloudflare resources

- Pages project: `leichtys-family`
- Production hostname: `www.leichtys.com`
- Redirecting apex: `leichtys.com`
- Pages development hostname: `leichtys-family.pages.dev`
- D1 database: not created
- R2 bucket: not created
- Turnstile widget: not created

DNS, SSL, nameservers, and redirect rules are managed outside this repository and should not be changed for ordinary site deployments.

## Security and privacy

- Never add email addresses, telephone numbers, invitation tokens, RSVP records, or living-person details to public JSON or generated HTML.
- Keep secrets in local ignored files or Cloudflare environment/secret storage.
- `.env`, `.env.*`, `.dev.vars`, and `.dev.vars.*` are ignored; `.env.example` contains names only.
- The public site sets a restrictive Content Security Policy and related browser security headers through `_headers`.
- Historical facts must have a source. Placeholder content must remain clearly labeled.

## Future RSVP backend

When registration work begins, use Cloudflare Pages Functions with D1, version-controlled migrations, server-side validation, parameterized queries, rate limiting, and Turnstile. Keep preview and production data separate. Do not expose the database to browser JavaScript.

Document the D1 resource name, bindings, migration commands, and environment strategy here when those resources exist.

## Data backup and portability

Current public content is fully recoverable from Git. Web-ready media and metadata should remain portable and versioned where practical; large original photographs and videos should be preserved separately.

When D1 is introduced, add exact commands here for:

- schema migration
- local development seeding
- production SQL export
- RSVP CSV export
- restore verification

Do not rely on an undocumented production-only schema.

## Disaster recovery

If the Cloudflare Pages project is lost:

1. Create or recover a Pages project connected to `leichtyjl/leichtys-family`.
2. Set `main` as the production branch.
3. Use the repository root as the static output; no framework build is required for the committed pages.
4. Reattach the documented custom domains only after reviewing the current DNS and redirect configuration.
5. Verify HTTPS, apex-to-`www` redirects, headers, routes, and responsive behavior.

Domain registration remains with IONOS. DNS and hosting are managed by Cloudflare.
